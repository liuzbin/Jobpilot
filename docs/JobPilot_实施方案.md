## 一、核心价值主张

在继续往下写设计细节之前，先把一件事定下来，因为它会反过来约束后面所有的设计取舍：JobPilot 的核心价值不是"帮用户更快地投更多份简历"，而是帮用户对照市场真实需求（也就是海量真实 JD）看清楚自己当前的能力边界——哪些是已经具备、值得被更好地表达出来的，哪些是相关但还没真正做过、值得针对性补齐的——并且真的推动用户去补上这个差距。效率工具解决的是"把已有的东西更快地包装出去"，JobPilot 要解决的是"用户借助这个工具，能力被放大了、短板被看见了、并且被实实在在地补上了一部分"。这句话是产品定位，也是后续所有对外宣传（落地页、一句话介绍、演示脚本）要反复讲的同一件事，不是锦上添花的附加特性——效率是这个价值主张带来的副产品，不是主张本身。

这个定位不是一句空话,它直接决定了几处已经拍板或正在设计的机制:

打分引擎（Phase 1 已实现）产出的不只是"这份 JD 我该不该投"这一个分数，报告里的劣势点列表本身就是一份"相对这个市场机会,我现在缺什么"的诊断书,这是"看清楚短板"的第一层。

画像深化和简历重制（Phase 2,本文档下面详述）里的"技能延伸建议"机制,落点不是让 LLM 悄悄帮用户在简历上造假,而是让用户先看到一条具体、可执行的差距——"这个技能和你某个真实项目的技术背景相关,值得你去补"——由用户自己确认之后再去做针对性的知识补齐。简历上多出来的那一行字,背后对应的应该是用户真实发生过的一次能力补齐动作,工具在这里更像一个"精准指出该往哪里使劲的教练",而不是简历美化机器。这是"补上短板"这一层。

认领技能库（见五、核心模块详细设计）明确不影响 Phase 1 打分引擎的客观分数,是为了保证"诊断"这一层永远诚实:用户不能靠"往简历里写点什么"来让系统误以为自己已经不缺这项能力了,只有真正完成了知识补齐,下一次面对同类 JD 时,差距才会名副其实地缩小。这道边界是"诚实"这条价值主张能够成立的前提,不能因为工程上方便就打破。

## 二、目标与范围

JobPilot 是一个运行在用户本地电脑上的求职辅助 Agent 工具，由 Chrome 插件（Manifest V3）与本地常驻应用（下称"本地 App"）两部分组成，不依赖任何云端服务器或云数据库，所有数据（画像、JD 历史、题库、简历版本）都保存在用户本地的 SQLite 文件中。核心能力覆盖五个环节：结构化用户画像的维护、JD 匹配打分、定制化简历重制、投递页面自动填表、以及贯穿这些环节的多模型调度，这五个环节共同服务于第一节说的那个核心价值——每个环节都应该既能帮用户把事情做得更快，也能帮用户更清楚地看见自己和市场要求之间的真实距离。

第一阶段（Phase 0 + Phase 1）的验收目标是打通"上传简历建画像 → 粘贴 JD → LLM 结构化打分 → 输出报告"这条最短闭环，已经完成。插件自动抓取 JD、自动填表放在更后续的阶段，简历重制原计划也在后续阶段，但整体数据模型从一开始就按最终形态设计，避免后期返工。

## 三、总体架构

系统分两大运行体：Chrome 插件负责"触手"职责，即读取网页内容（JD 文本、ATS 表单 DOM）和向网页写入数据（自动填表），并提供 Side Panel 作为用户交互界面；本地 App 是常驻在用户电脑上的服务进程，负责数据持久化、Prompt 编排、调用可配置的大模型、生成简历文件，并对外暴露一个仅监听 `127.0.0.1` 的本地服务，同时提供一个可以直接在本地浏览器打开的 Dashboard（Jinja2 服务端渲染）。

两者之间的通信采用本地 WebSocket（用于心跳保活和插件主动推送 JD/表单数据）加本地 REST API（用于插件拉取画像数据、查询历史）的组合，全部限定在 `127.0.0.1`，并在插件首次与本地 App "配对"时交换一个随机生成、落盘保存的 pairing token，之后每次请求都带上该 token 校验，同时后端会校验请求的 `Origin` 头必须是本插件的 `chrome-extension://` 来源。Dashboard 页面是用户直接用浏览器打开的普通页面，走的是另一套更轻量的同源校验（详见 `app/api/deps.py` 的 `require_local_browser`），不复用插件这套配对 token 机制——这是 Phase 1 落地时确认的设计，具体原因见 `docs/DEVELOPMENT_LOG.md` Phase 1 章节。

本地 App 内部分三层：最底层是 SQLite + SQLAlchemy 的数据层；中间是业务服务层（`app/services/`），包含画像抽取与合并、JD 结构化解析、匹配打分、简历重制等模块，每个模块按需调用"轻量模型"或"重量模型"两个可配置的模型槽位（通过 `LLMClient` 协议统一抽象，`app/core/llm_client.py` / `llm_factory.py`）；最上层是 FastAPI 暴露的 API，同时服务插件的请求（`/api/*`、`/ws/*`）和 Dashboard 页面（`/dashboard/*`）。

## 四、数据模型设计

以下是核心表结构（SQLite），Phase 0/1 已落地的表结构见代码 `backend/app/models/tables.py`，本节同步反映 Phase 2 计划新增的字段和表。

**用户基本信息表 `profile_basic`**：单行记录（本地单画像假设），字段包括姓名、目标职位、学历、电话、邮箱、linkedin_url、github_url、学校、工作经验年限、当前所在地、目标工作地、是否有当地工签、更新时间等格式固定的字段，每个字段独立列存储，便于校验和填表时精确取值。已在 Phase 0/1 落地。

**工作经历树 `experience_entry`**：按 A/B/C 三层结构落地为一张自关联表加一张贡献句表。`experience_entry` 表存 A 层（公司）和 B 层（项目+岗位+时间区间），用 `parent_id` 做层级关联，`level` 字段区分 A/B。已在 Phase 0/1 落地。**Phase 2 计划在 B 层新增两个字段**：`background_notes`（大文本，"项目背景与理解"，承载简历重制阶段做技能延伸判断所需的上下文——项目背景、技术架构、数据规模、用户自己认为有挑战或值得展开的地方）和 `background_qa`（JSON，追问式访谈的原始问答记录，用于追溯 `background_notes` 是怎么来的、方便用户后续追加）。这两个字段不是要求用户一次性写完的空白表单，而是通过"追问式访谈"机制逐步填充，详见五、核心模块详细设计。

**贡献句表 `experience_bullet`**：C 层，每一行是一句具体贡献，外键指向所属的 B 层条目，挂一个 `tags` 字段（JSON 数组，冗余存储 A 层公司名和 B 层岗位/项目名）。已在 Phase 0/1 落地。**Phase 2 计划新增三个衍生字段**：`keywords`（JSON 数组，这句话里出现的技术/领域关键词）、`action_summary`（这句话描述的核心行为，短语级别）、`result_summary`（这句话描述的结果/成效，可为空）。三个字段在简历合并入库时由轻量模型从原始 `content` 拆解得到，`content` 本身保持不变、永远是唯一的事实来源，三元组只是从它提炼出来、用于匹配和重组的索引。这个设计的动机是：HR/ATS 筛简历本质上是在抓"关键词、做了什么、什么结果"这三样东西，而不是逐句做阅读理解，让简历重制模块也按同样的颗粒度组织内容，既更贴近真实筛选逻辑，也让"JD 要的这个关键词，画像里到底有没有"这个判断变得直接可查，不用每次都重新读一遍整句话去猜。

**认领技能库 `claimed_skill`（Phase 2 新增表）**：记录用户确认接受过的"技能延伸建议"，字段包括技能名（对应关键词）、关联的 B 层项目条目 `experience_entry_id`、构造出的行为 `action_summary`、构造出的结果 `result_summary`、判断依据（为什么认为这项技能和该项目背景相关）、首次触发这条建议的 `jd_record_id`（可为空）、认领时间。这张表跨 JD 复用：下次别的 JD 又要求同一个技能时，系统可以直接从这里取一个起点，不用重新推导，但每次生成简历时仍会把它列出来做一次轻量确认，而不是自动静默采用。**这张表的内容明确不参与 Phase 1 打分引擎（`compute_score`）的计算**，原因见第一节"核心价值主张"——打分要对用户保持诚实，不能被简历重制阶段的延伸内容反向影响。

**JD 记录表 `jd_record`**：存公司、岗位、JD 全文、地点、来源链接、附加信息原文和解析后的结构化字段，加一个 `status` 字段表示状态机（`pending` / `analyzing` / `analyzed` / `tailored` / `applied`）。已在 Phase 0/1 落地。

**打分结果表 `match_score`**：外键关联 `jd_record`，存三个维度的分项分数、扣分加分明细（JSON）、总分、优势点列表、劣势点列表、以及本次打分所用的模型标识和 prompt 版本号。已在 Phase 1 落地，计算逻辑是纯函数 `compute_score`，同样输入无论调用多少次输出必须完全一致（已有 pytest 用例锁定）。

**简历版本表 `resume_version`**：外键关联 `jd_record`，存 K 值、生成的结构化简历 JSON、渲染出的 Markdown 文本、PDF 文件路径、所用的简历风格 `style_id`、生成时间。一个 JD 可以对应多个不同 K 值或不同风格的版本。表结构已在 Phase 0 建好，生成逻辑待 Phase 2 实现。

**题库表 `qa_bank`**：存问题原文、问题的 embedding、用户填写的答案、答案来源、最近使用时间、使用次数。表结构已在 Phase 0 建好，收集流程待 Phase 2 实现。

**模型配置表 `model_config`**：存"轻量化"和"重量化"两个槽位各自的 `base_url`、`model_name`，API Key 不直接存这张表，落地时改用对称加密（Fernet）存本地文件而不是 OS keyring，原因见 `docs/DEVELOPMENT_LOG.md` Phase 1 章节。已在 Phase 0/1 落地。

## 五、核心模块详细设计

### 5.1 画像模块

简历上传后的处理流程：本地解析 PDF/DOCX/TXT/MD 提取纯文本，交给"轻量模型"做结构化抽取，按 A/B/C 三层输出。Phase 1 落地时，为了先跑通端到端打分闭环，合并逻辑做了简化：不弹交互式"合并/替换"选择，而是按公司/项目名做不区分大小写的模糊匹配自动合并、按去重后的精确文本自动去重（详见 `app/services/profile_service.py`），交互式的手动合并/替换选择仍然保留在 Phase 2 的待办范围内。

用户通过对话补充信息时，走同样的"轻量模型抽取 → 定位到对应 B 层条目 → 追加 C 层句子"流程。

关于"连续性"：画像是 SQLite 里的持久化数据，本地 App 每次启动时直接从数据库加载最新状态，Agent 需要读取画像做匹配打分或简历重制时必须实时查询数据库拿最新快照，不缓存在长期运行的内存对象或对话历史里，保证画像更新后所有下游功能立刻感知到变化。已在 Phase 0/1 落地。

**以下为 Phase 2 新增设计（2026-09-10 讨论确定）：**

给 B 层新增"项目背景与理解"这个自由文本字段的目的，是给简历重制阶段的技能延伸判断提供足够厚的上下文——只有一句 bullet 撑不起"这个技能和这个项目是否属于同一技术圈子"这种判断。但这段文本不是让用户对着空白文本框独自写作文：系统（轻量模型）会先看这个项目现有的 bullet、项目名、岗位名，判断当前信息是否足够支撑后续的技能延伸判断，不够就生成几个有针对性的问题（比如"这个系统大概是什么数据规模/架构？""你具体负责数据接入、处理还是应用层？""除了 bullet 里写的，还用到过哪些核心组件？"），用户在 Dashboard 项目详情页里像聊天一样逐条回答（可以跳过），系统把问答整理成一段连贯文本写回 `background_notes`，原始问答保留在 `background_qa` 里方便复查和追加。这个访谈由用户在项目详情页手动点击"深化这段经历"触发，不在简历解析完之后自动弹出，避免一次性打断用户；同一个项目可以多次触发、逐步补充。

C 层贡献句在合并入库时，额外走一步轻量模型抽取，把每条 bullet 拆成"关键词 + 行为 + 结果"三元组存入 `keywords`/`action_summary`/`result_summary`，原始 `content` 不变。这一步紧接在现有的 `merge_parsed_experience` 之后执行，对新增和已存在的 bullet 都适用（已存在的 bullet 如果还没有三元组衍生字段，画像深化阶段可以补跑一次）。

### 5.2 JD 匹配与打分模块

JD 由用户手动粘贴全文，轻量模型做结构化解析，LinkedIn 附加信息行走纯正则规则解析（不经过 LLM，保证这部分结果绝对稳定）。打分逻辑分成"LLM 负责语义判断"和"代码负责确定性计算"两部分：技能契合度判断交给重量模型，硬性要求扣分、年限差扣分、加分技能这类数值计算全部由纯函数 `compute_score` 完成，LLM 只负责抽取事实/给出语义判断，不参与数值运算，保证同一份 JD 和画像重复打分结果完全一致。已在 Phase 1 落地并有 pytest 用例覆盖确定性要求（连续调用 5 次断言输出完全相同）。

### 5.3 简历重制模块

关于 K 值机制：K=0 只做真实内容的重排和筛选，不做技能延伸；K=10 是在"事实性硬信息不可篡改"这条底线内、最大幅度地做技能延伸和措辞贴合；K=1-9 按比例在两端之间过渡。底层基线约束（贯穿所有 K 档、不因 K 值高低而放松）：延伸出的任何具体贡献、技术动作，都必须能在画像里找到可追溯的真实项目/技术背景作为依据，不允许凭空产生一个用户完全没有接触过的技术方向，也不允许编造不存在的公司、职位、任职时间、学历或证书。生成后有一道自动校验步骤：用规则+轻量模型比对生成内容中出现的公司名/职位名/时间/学历字段是否与画像原始数据一致，不一致则拒绝输出并重试。这道校验是自动的、事后的，保护"事实性硬信息"，这一段是 v1 就定好的设计，Phase 2 落地时不做改动。

**以下为 Phase 2 新增设计（2026-09-10 讨论确定），细化"延伸"这一档具体怎么执行：**

结合 5.1 里的关键词/行为/结果三元组，简历重制在生成某个 JD 对应的版本时按下面的逻辑组织内容：JD 解析出的核心技能/关键词，逐个去和画像里所有 bullet 的 `keywords` 字段比对。命中的，直接取对应 bullet 的三元组，用 JD 的措辞习惯重组"行为"和"结果"的表达——这是较低 K 档位的行为，内容都是真实三元组，只调整表达。没命中、但某个项目的 `background_notes` 显示技术背景相关（比如 JD 要 Spark，某个项目背景描述里提到了同量级的批处理/ETL 场景），且当前 K 值允许延伸时，由重量模型构造一条"建议三元组"：关键词是 JD 要的那个词，行为基于项目背景和目的推导，结果的量级参照用户在其他真实 bullet 里已经写出的结果区间校准（不能给一个明显超出用户历史量级的数字，比如其他项目结果都在 15%-20% 提升区间，新构造的结果也应该落在类似可信区间）。

这条构造出来的建议三元组，连同关联项目、判断依据一起，先作为一条"待确认建议"返回，不直接进入生成的简历。用户在 Dashboard 上逐条查看、接受/拒绝/编辑，只有确认过的才真正写进这一版简历。这道确认关卡和上面说的事实校验是两件不同的事、并行存在：事实校验是自动的、事后的，保护事实性硬信息，任何 K 值下都不允许 LLM 碰；这道确认关卡是人工的、事前的，保护延伸出来的技能主张——一条延伸内容是否可信、用户是否真的愿意为它去补课，这件事只有用户自己能判断。

用户确认过的建议三元组持久化进 `claimed_skill` 表，下次别的 JD 再要求同一个技能时可以直接复用这套三元组做起点，但每次生成简历时仍会列出来做一次轻量确认，不自动静默采用。`claimed_skill` 的内容不参与 `compute_score` 的计算，理由见第一节。

生成管线上，重量模型输出结构化的简历 JSON，本地 App 用 Jinja2 渲染成 Markdown（供预览、手动微调）和对应 `style_id` 的 HTML 模板，再用 WeasyPrint 渲染成 PDF。当前先实现一套风格模板，模板和渲染逻辑用 `style_id` 解耦。

### 5.4 简历投递自动化填表

（与 v1 一致，未变更，留待 Phase 4 实现。）内容脚本注入 ATS 页面后，针对 Workday、Greenhouse、Lever 各维护一份选择器规则库，规则库之外的未知 ATS 走通用兜底策略：遍历页面表单元素，读取关联的标签文本，用轻量模型映射到画像字段，本地 App 格式化后回传给插件写入。长文本主观题走 `qa_bank` 的 embedding 相似度检索（应用内用 numpy 计算 cosine similarity），相似度高于 0.85 直接回填（轻量模型微调措辞），低于 0.85 弹悬浮提示让用户手写，写完存入 `qa_bank` 形成自我迭代闭环。最终"提交"按钮由用户手动点击，插件只监听该点击事件，不做无人值守的自动提交。

### 5.5 本地 App 与插件基座

（已在 Phase 0/1 落地，架构与 v1 一致。）本地 App 用 Python + FastAPI 实现，数据层用 SQLAlchemy + Alembic 管理 SQLite schema 演进。插件端用 Chrome Manifest V3，`background` 用 service worker 维护与本地 App 的 WebSocket 长连接和断线重连/心跳逻辑，UI 用 Chrome 的 Side Panel API。配对流程：本地 App 首次启动生成 pairing token 落盘，插件通过配对页面获取该 token，之后所有请求带上它。

### 5.6 多模型编排

（已在 Phase 0/1 落地，架构与 v1 一致。）两个可配置槽位——"轻量模型"和"重量模型"，各自独立配置 `base_url`、`model_name`、API Key（Key 加密存本地文件），只要目标服务提供 OpenAI 兼容的 Chat Completions 接口就可以直接接入。业务代码通过 `LLMClient` 协议统一调用，不感知具体用的是哪家模型。Phase 2 新增的追问式访谈问题生成、bullet 三元组抽取用轻量槽位（偏抽取），技能延伸建议的构造和简历重制的最终生成用重量槽位（偏语义推理）。Dashboard 用量统计面板留待 Phase 5 打磨阶段实现。

## 六、关键设计决策记录

| 议题 | 原方案的问题 | 最终决策 |
|---|---|---|
| 简历重制 K=7-10 档（v1） | 原描述允许"推演出用户完全没做过的具体技术动作"，属于编造虚假履历内容 | 改为 K=0~10 连续谱，任何 K 值下事实性硬信息不可篡改，延伸内容必须可追溯到真实项目/技术背景，生成后加自动校验步骤兜底 |
| 主观题相似度检索用 pgvector（v1） | pgvector 依赖 PostgreSQL，与"零云端、纯本地"矛盾 | 改为 SQLite 存 embedding + 应用内 numpy 计算 cosine similarity |
| LLM 接入方式（v1） | 原方案写死具体厂商 | 改为"轻量"、"重量"两个可自由配置的 OpenAI 兼容槽位 |
| API Key 存储（Phase 1 落地时调整） | 原方案设想用 OS keyring，Linux 服务器/CI 环境常没有可用的 Secret Service | 改为对称加密（Fernet）存本地文件，核心诉求"不明文落库"不变，后续要换回 keyring 只需替换 `secrets.py` 内部实现 |
| Dashboard 鉴权方式（Phase 1 落地时新增） | 若直接复用插件的配对 token 鉴权，Dashboard 普通浏览器导航会被自己的鉴权规则挡在门外 | 新增更轻量的 `require_local_browser`：GET 不鉴权，POST 只做同源校验，与插件的配对 token 鉴权分离 |
| 画像合并交互（Phase 1 落地时简化，Phase 2 补上） | 原方案设想有冲突时弹交互式"合并/替换"选择 | Phase 1 先做成按名称模糊匹配+精确去重的自动合并，跑通闭环；交互式选择放到 Phase 2 |
| 项目背景信息的输入方式（本次新增） | 一开始设想让用户直接写自由文本，容易写得潦草、信息量不够支撑后续技能延伸判断 | 改为"追问式访谈"：系统先根据已有 bullet 判断信息缺口，针对性提问，用户回答后系统整理成 `background_notes` 大文本；访谈由用户在项目详情页手动触发，不自动弹出 |
| bullet 的内容组织颗粒度（本次新增） | 只把 bullet 当整句自然语言处理，简历重制时模型缺乏抓手判断"这句话是否命中 JD 关键词"，也难以仿照真实笔法构造延伸内容 | bullet 入库时额外抽取"关键词+行为+结果"三元组衍生字段，原文 `content` 不变；简历重制无论是重组已有内容还是构造延伸内容，都按同样的三元组颗粒度组织，且延伸结果的量级参照用户其他真实 bullet 的历史区间校准 |
| 技能延伸的产生和落地方式（本次新增） | 若由模型在生成阶段直接、静默地把延伸技能写进简历，用户可能意识不到哪些是延伸出来的，也就没法有意识地去补课 | 延伸出的每条建议三元组必须先展示判断依据、经用户逐条确认后才写入简历；确认过的持久化进 `claimed_skill` 表供以后复用，但每次生成仍需轻量确认，不自动静默采用 |
| 认领技能库是否计入打分（本次新增） | 直觉上"用户认领了某技能"似乎应该让匹配分更高 | 明确不计入：`compute_score` 只读真实画像数据，打分要对用户保持诚实，这是"核心价值主张"（第一节）能够成立的前提 |
| 单画像/多画像（v1） | 未定 | 单画像方案（一台电脑一份画像），MVP 更简单，已在 Phase 0 落地 |

## 七、技术栈总览

本地 App：Python 3.11+、FastAPI（REST + WebSocket）、SQLAlchemy + Alembic、SQLite、Pydantic、pdfplumber + python-docx（简历解析）、Jinja2 + WeasyPrint（简历渲染，WeasyPrint 待 Phase 2 引入）、cryptography（密钥加密存储）、numpy（相似度计算，待 Phase 4 引入）。

浏览器插件：Chrome Manifest V3、JavaScript、Side Panel API、内容脚本 + 后台 service worker、原生 WebSocket 客户端。

Dashboard：Jinja2 服务端渲染 + 少量原生 JS，已在 Phase 1 落地。

## 八、分阶段实施计划

**Phase 0 — 基座打通（已完成，见 `docs/DEVELOPMENT_LOG.md`）**：FastAPI 项目骨架、SQLite + Alembic 初始迁移、Chrome 插件 MV3 骨架、插件与本地 App 的配对+心跳链路。

**Phase 1 — 端到端打分闭环（已完成，见 `docs/DEVELOPMENT_LOG.md`）**：简历上传解析入库、JD 粘贴入库与结构化解析、打分引擎、模型配置页面、最简 Dashboard（画像编辑、JD 列表与详情、一键分析、模型配置）。56 条 pytest 用例覆盖，含确定性打分的专项测试。

**Phase 2 — 画像深化与简历重制（当前阶段，本版本文档细化的范围）**：

1. 工作经历树的增删改交互补全（合并/替换 diff 逻辑，Phase 1 暂时简化成的自动合并在这一阶段补上交互式选择）。
2. B 层新增 `background_notes`/`background_qa` 字段，实现"追问式访谈"服务：分析已有背景信息缺口 → 生成针对性问题 → 用户在项目详情页作答 → 合并写回 `background_notes`。
3. C 层 bullet 入库时抽取"关键词+行为+结果"三元组衍生字段（`keywords`/`action_summary`/`result_summary`）。
4. 实现题库表 `qa_bank` 和最初建画像时的问答收集流程。
5. 实现简历重制模块：K 值 0-10 驱动的结构化生成、Markdown+PDF 双产物、事实字段护栏校验（沿用 v1 设计不变）、技能延伸建议的逐条确认流程（新增）、认领技能库 `claimed_skill` 及其跨 JD 复用（新增）、一套简历风格模板。

自测方式：对同一份画像+JD 分别跑 K=0/K=5/K=10 三档，人工核对 K=0 确实只是重排、K=10 的延伸建议是否都能在项目背景里找到依据、且必须经用户确认才生效；写自动化校验测试，故意在生成结果里注入一个不存在的公司名，断言护栏校验能拦截；构造一个"`claimed_skill` 里已认领某技能"的用例，断言打分引擎 `compute_score` 的分数不受影响（回归测试，守住"打分诚实"这条底线）；检查生成的 PDF 在不同长度简历下排版是否稳定不错位。

**Phase 3 — 插件抓取 JD**：（与 v1 一致）LinkedIn 职位详情页的内容脚本解析，一键发送给本地 App 走已有的打分链路。

**Phase 4 — 自动化填表**：（与 v1 一致）Workday/Greenhouse/Lever 选择器规则 + 通用兜底识别、题库相似度检索与自动填充、提交按钮监听与状态推进。

**Phase 5 — 打磨阶段**：（与 v1 一致）简历风格自定义能力、本地 App 打包分发、用量统计面板、整体异常处理和用户提示文案完善。

## 九、风险与待解决问题

简历重制护栏的自动校验设计为"规则+轻量模型比对事实字段"，实际效果需要在 Phase 2 用真实案例测试后再评估是否需要加强。ATS 选择器规则库需要持续维护，留待 Phase 4 设计"规则库版本化+快速修复"机制。单画像/多画像问题已在 Phase 0 确认为单画像方案。

**本次新增风险点**：追问式访谈如果每个项目都问很多轮，可能变成用户的负担，需要在 Phase 2 实现时控制单次访谈的问题数量（建议 3-5 个）、允许随时跳过，并观察真实使用反馈再调整；技能延伸建议的"判断依据"质量依赖重量模型的推理能力，如果模型倾向于给出牵强的关联（比如把明显不相关的技术也说成"相关"），需要在 Prompt 里加约束并在真实案例上人工核查，必要时收紧触发条件（比如要求项目背景描述里有更明确的技术信号才触发建议，而不是仅凭 JD 关键词反推）。
